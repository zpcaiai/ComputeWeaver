# Evidence Standard

## Why this exists

Generated specifications and code volume do not prove functionality. Evidence must come from commands run against the implementation on the exact commit being evaluated.

## Required evidence metadata

Every batch evidence directory must contain `manifest.json`:

```json
{
  "batch": "Bxx",
  "git_commit": "<sha>",
  "generated_at": "<UTC>",
  "environment": "<local|ci|staging>",
  "commands": [],
  "artifacts": [],
  "mandatory_gates": {
    "build": "PASS|FAIL",
    "tests": "PASS|FAIL",
    "contracts": "PASS|FAIL",
    "security": "PASS|FAIL|NOT_APPLICABLE",
    "scenario": "PASS|FAIL|NOT_APPLICABLE"
  }
}
```

## Evidence hierarchy

Strong evidence:

1. Reproducible test reports generated by CI.
2. Solver logs plus model/input hashes.
3. API/event contract test results.
4. Scenario event archives and evaluator outputs.
5. Security, load, chaos and restore reports.

Supporting evidence:

- Structured logs.
- Database migration records.
- Trace exports.
- Generated reports reconciled to source data.

Insufficient by itself:

- Screenshots.
- File counts.
- A successful package validator.
- A written statement that tests passed.
- Mock-only demonstrations.
- Unexecuted test files.

## Completion rules

A batch remains `EVIDENCE_PENDING` when implementation exists but evidence is incomplete.

A batch remains `BLOCKED` when a mandatory dependency or external interface is unavailable and cannot be safely simulated behind the declared contract.

A batch may be `COMPLETE` only if every DoD item is explicitly PASS and all mandatory evidence artifacts exist.

## Anti-fabrication checks

- Evidence references the current Git commit.
- Test timestamps are after the implementation changes.
- CI job URL or local command is recorded.
- Solver output is tied to immutable input/model hashes.
- Reports contain source run IDs.
- Skipped tests and waivers are enumerated.
