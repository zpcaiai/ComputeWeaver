# B15 — Policy, Constraint, Risk and Plan Lifecycle Governance

## 1. Mission

Centralize hard/soft constraints, policy conflicts, risk classification, plan validation, versioning, comparison and release gates.

## 2. Completion truth rule

Codex MUST NOT mark this batch `COMPLETE` because files were created or because code appears plausible. Completion requires all of the following:

1. Production implementation exists at the declared repository paths.
2. All required tests execute and pass.
3. Evidence artifacts are generated by the actual commands and reference the current commit.
4. No required interface is a stub, mock-only endpoint or unconditional success path.
5. The batch-specific Definition of Done and handoff contract are satisfied.

Allowed statuses are:

```text
NOT_STARTED
IMPLEMENTING
BLOCKED
EVIDENCE_PENDING
COMPLETE
```

## 3. Dependencies

`B05,B13,B14`

Codex must verify dependency evidence before changing this batch to `IMPLEMENTING`. When a dependency interface is unavailable, create a typed temporary adapter behind the declared contract and keep the batch `BLOCKED` or `EVIDENCE_PENDING`; do not silently invent incompatible APIs.

## 4. Inputs

- Business SLA and quota rules.
- Optimization constraint catalogue.
- Automation risk levels and approval boundaries.
- Plan states and concurrency requirements.

## 5. Scope and required code modules

- `packages/policy/dsl`: versioned policy expressions and scopes.
- `packages/policy/engine`: evaluate, explain and conflict-detect.
- `packages/constraints/catalog`: IDs, severity, owner and enforcement mode.
- `packages/risk/classifier`: L0-L4 action and plan risk.
- `packages/plans/lifecycle`: draft, validate, approve, activate, supersede.
- `packages/plans/diff`: job, power, SOC, cost and risk changes.
- Policy and plan administration UI.

## 6. Required interfaces

- `POST /v1/policies/validate`, `/publish`, `/dry-run`.
- `POST /v1/plans/{id}/validate`, `/compare`, `/submit-approval`.
- Events: `PolicyPublished`, `PolicyConflictDetected`, `PlanValidated`, `PlanSuperseded`.
- Validation result includes hard violations, warnings, active policies, risk and required approvers.

All write interfaces must specify authentication, authorization, tenant/site scope, idempotency behavior, validation errors, audit event and rollback/compensation behavior where applicable.

## 7. Implementation workflow

1. Inspect the repository and dependency evidence; record the exact commit.
2. Produce or update an implementation plan mapping every required module to concrete files.
3. Implement domain models and pure logic before transport and UI code.
4. Implement APIs/events/adapters using B02 contracts.
5. Add migrations, seed fixtures and configuration documentation.
6. Add tests before marking interfaces complete.
7. Run the batch verification commands from a clean state.
8. Generate the evidence pack automatically.
9. Review open TODO, FIXME, skipped tests and mock-only paths.
10. Update the batch manifest and handoff notes.

## 8. Required tests

- Conflicting policies are detected before publication.
- Hard constraints cannot be downgraded by local users.
- Plan lifecycle transition and optimistic-lock tests.
- Stale plan rejected after material state change.
- Policy dry-run across historical and simulated scenarios.
- Tenant/site scope isolation.

Minimum test classes:

```text
unit
property/algorithm
API or event contract
integration
negative/failure
security/authorization where relevant
scenario or regression
```

Skipped tests require an explicit waiver in `evidence/{b['id']}/waivers.json`; a waiver cannot cover a mandatory safety gate.

## 10. Quality and safety gates

- No secrets, production credentials or real device write targets in fixtures.
- No silent fallback that changes a hard constraint into a soft preference.
- No LLM-generated value may bypass typed validation or the mathematical/safety layer.
- All externally visible errors use the shared error contract.
- State-changing operations are auditable.
- Data lineage and version provenance are preserved.
- New dependencies are locked, scanned and documented.
- Public interfaces receive contract tests.
- Failed mandatory gates block completion.

## 11. Definition of Done

- All optimizer and execution constraints resolve to a governed catalogue entry.
- Policies are versioned, scoped, explainable and dry-runnable.
- Plans cannot become active without validation.
- Risk classification determines approval and execution requirements.
- Historical decisions retain the exact policy versions used.
